# Treasury Operations Center — Users v11

## Як увімкнути

Це нова версія кабінету з особистими акаунтами. Код підготовлено й перевірено локально; його ще не розгорнуто на вашому Railway.

1. Збережіть резервну копію PostgreSQL та поточного робочого релізу.
2. Оновіть існуючий репозиторій файлами архіву. Папки `server`, `docs`, `scripts`, `tests`, `package.json` і `package-lock.json` належать одному релізу.
3. Додайте змінні нижче до Railway. У `APP_ORIGIN` вкажіть адресу сервісу без шляху. Backend тепер також віддає HTML, тому вхід і API працюють на одному домені.
4. Зробіть Deploy. Відкрийте саме Railway URL, наприклад `https://eth-pending-monitor-production.up.railway.app/`. Стара GitHub Pages адреса не є адресою входу у v11.
5. Натисніть Create account, зареєструйте **той самий email**, який указано в `BOOTSTRAP_OWNER_EMAIL`, і підтвердьте його за листом.
6. У Security & accounts налаштуйте Authenticator: введіть пароль, перенесіть setup key у застосунок, введіть шестизначний код. Збережіть десять резервних кодів — повторно вони не показуються.
7. У секції Existing personal workspace натисніть Import previous workspace з новим кодом 2FA. Імпорт доступний лише власнику один раз; стара історія в базі залишається. Якщо ви вже зберегли нові wallet settings, імпорт збереже їх, а не перезапише старими.
8. Додайте Bitget у Security & accounts. Глобальні Bitget-ключі з Variables більше не використовуються. Створіть окремий read-only ключ і введіть його в захищену форму.
9. Перевірте власний кабінет. Для допуску інших користувачів змініть `REGISTRATION_OPEN=true`.

## Змінні Railway

| Змінна | Значення |
|---|---|
| `APP_ORIGIN` | Ваш HTTPS Railway URL або власний домен, без шляху |
| `BOOTSTRAP_OWNER_EMAIL` | Ваш email для першої реєстрації та імпорту |
| `CREDENTIAL_ENCRYPTION_KEY` | Випадкові 32 байти, закодовані base64; команда нижче |
| `RESEND_API_KEY` | API key вашого Resend-акаунта для листів підтвердження та відновлення |
| `EMAIL_FROM` | Наприклад `Treasury <alerts@your-domain.com>`; відправник має бути дозволений у Resend |
| `REGISTRATION_OPEN` | `false` на старті; власник усе одно може зареєструватися; `true` для тестових користувачів |
| `MAX_USERS` | `25` за замовчуванням для обмеженої бети |
| `NODE_ENV` | `production` на Railway |

Залиште наявні `DATABASE_URL`, `ALCHEMY_WSS_URL`, `ETHERSCAN_API_KEY`, `CRYPTOCOMPARE_API_KEY`, VAPID-змінні. `ADMIN_TOKEN` та глобальні `BITGET_API_*` у v11 не дають доступу до приватних даних і не використовуються для підключень користувачів.

Згенеруйте ключ локально, скопіюйте результат лише в Railway і збережіть резервну копію в менеджері паролів:

```sh
node -e "console.log(require('node:crypto').randomBytes(32).toString('base64'))"
```

Не генеруйте новий ключ при кожному деплої. Втрата або заміна ключа без міграції зробить збережені exchange credentials і TOTP secrets недоступними. Для email використовується Resend; FormSubmit не є запасним способом доставки посилань входу/відновлення.

## Що реалізовано

- Реєстрація, підтвердження email, повторне надсилання листа, вхід, вихід, зміна та відновлення пароля.
- Паролі через scrypt; випадкові сесії, у базі зберігається лише SHA-256 ідентифікатора сесії. Cookie: HttpOnly, Secure у production, SameSite=Lax. Захист змін через перевірку Origin і CSRF-token.
- Сесія живе до 7 днів, з тайм-аутом неактивності 24 години; до 10 сесій на користувача. Список пристроїв і відкликання сесії. Зміна/відновлення пароля відкликають усі сесії.
- TOTP із захистом від повторного використання того самого часового кроку, вікном ±30 секунд і десятьма одноразовими recovery codes. Скидання пароля не обходить увімкнену 2FA.
- AES-256-GCM для API Key, Secret, Passphrase і TOTP secret. AAD прив’язує шифротекст до власника й запису. Ключ шифрування не зберігається в PostgreSQL.
- Особисті налаштування, транзакції, курсор сканування, логи сповіщень і push-підписки. Фонові монітори прив’язані до власника. Вихід/відкликання сесії видаляє її push-підписки.
- Особисті Bitget-підключення — до 3 на користувача. Перед додаванням обов’язкова 2FA. Перевірка read-only permission та доступу до Unified Account. Невідомі/непідтверджені права відхиляються; немає режиму пропуску перевірки.
- Видалення підключення з 2FA. Заміна ключів: видалити старе підключення та додати нове.
- Браузерні дані кабінету перебувають у пам’яті. Wallet sources, transfer drafts і налаштування дерева зберігаються на сервері для користувача. API-ключі не записуються в localStorage.
- Загальні gas analytics і новини використовують ключі платформи. Ліміти входу та API зберігаються в базі, новини кешуються, RPC-запити мають додатковий ліміт.
- Журнал безпеки за 30 днів. Зберігаються до 2000 останніх завершених транзакцій на користувача; pending не видаляються цією політикою. Створення нових таблиць не видаляє старі таблиці особистої версії.

## Перевірка і межі релізу

```sh
npm ci
npm run check
npm test
```

Усі 24 перевірки пройшли. Тести використовують PostgreSQL-сумісний PGlite та Chromium. Вони перевіряють ізоляцію користувачів, CSRF, заборону старого ADMIN_TOKEN, RFC-вектор TOTP, повторне використання кодів, зашифровані ключі, сесії, password reset, імпорт власника та роботу інтерфейсу.

Зовнішні Bitget і Resend у тестах замінені контрольованими відповідями. На живому Railway ще потрібно перевірити доставку листа з вашого відправника, фактичну відповідь Bitget щодо прав ключа, cookie через HTTPS та фоновий Alchemy-моніторинг. Перевірка permission використовує `/api/v2/spot/account/info`; якщо ваш тип акаунта не повертає підтриманий масив `authorities`, додавання буде відхилено до перевірки інтеграції, навіть якщо запит балансу працює.

Це реліз для закритої бети, не сертифікація безпеки. Залишайте одну Railway replica: кілька реплік наразі дублюватимуть фонові монітори. Для масштабування потрібен окремий спільний worker/черга та розподілений лідер. Монітор на кожного користувача споживає ресурси Alchemy; `MAX_USERS` обмежує початковий масштаб.

Якщо повертаєтеся до v10, нові користувацькі дані не переносяться назад автоматично. Старі таблиці залишаються, але нові сесії, ключі та історія живуть окремо.

Технічні орієнтири: [RFC 6238](https://www.rfc-editor.org/rfc/rfc6238), [OWASP Session Management](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html).
